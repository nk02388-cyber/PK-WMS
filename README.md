# BCL WMS

ระบบจัดการคลังสินค้าและบรรจุภัณฑ์ของ BIO-COSLAB สำหรับดูสต็อก รับเข้า จัดเก็บ เบิก รับคืน ตรวจนับ และติดตามงานจากเว็บเบราว์เซอร์

- **เข้าใช้งาน:** [BCL WMS บน Vercel](https://bcl-wms.vercel.app/) · [GitHub Pages](https://nk02388-cyber.github.io/bcl-wms/)
- **ซอร์สโค้ด:** [nk02388-cyber/bcl-wms](https://github.com/nk02388-cyber/bcl-wms)
- **สถานะเอกสาร:** ตรวจเทียบกับโค้ดใน `main` ณ 28 กันยายน 2026

## เริ่มใช้งาน

1. เปิดเว็บและเข้าสู่ระบบด้วยบัญชีที่ Admin กำหนด ผู้ใช้ย่อยใช้ **ชื่อผู้ใช้และ PIN ตัวเลข 6 หลัก** โดยไม่ต้องกรอกอีเมล
2. เลือกเมนูที่ได้รับสิทธิ์จากแถบด้านซ้าย บนมือถือใช้เมนูนำทางของหน้าเว็บ
3. ตรวจวันที่ข้อมูลและสถานะการเชื่อมต่อก่อนบันทึกรายการ ข้อมูล Stock, พาเลต และแผนรับเข้าอาจอัปเดตคนละเวลา

Admin ใช้ไอคอนบัญชีที่มุมขวาบนเพื่อเพิ่มหรือลบผู้ใช้ย่อย และเลือกสิทธิ์เป็นรายเมนูได้ทั้งตอนสร้างบัญชีและภายหลัง บัญชีใหม่เริ่มต้นที่สิทธิ์ Dashboard; บัญชีเดิมที่มีอยู่ก่อนระบบสิทธิ์รายเมนูคงสิทธิ์เดิมไว้ Admin ยังใช้รหัสผ่านของตนเอง ไม่ใช้ PIN 6 หลักของผู้ใช้ย่อย

## งานหลักในระบบ

| เมนู | ใช้ทำอะไร |
| --- | --- |
| Dashboard | ดูมูลค่าสต็อก พื้นที่จัดเก็บตามอาคาร อายุพาเลต และกราฟมูลค่าตามคลัง/หมวดสินค้า; ผู้มีสิทธิ์ที่เกี่ยวข้องอัปเดต Stock จาก `.xlsx`, `.xls`, `.csv` หรือ `.txt` ได้โดยใช้ Update PIN |
| รับเข้าและจัดเก็บ | บันทึกรับสินค้า แบ่งจำนวนลงพาเลต พิมพ์ป้าย FM-ST-019 และยืนยันจัดเก็บเข้าตำแหน่ง |
| เบิกและรับคืนเบิก | ค้นหาสินค้าและตำแหน่ง ดูผังพาเลต บันทึกเบิก รับคืน ย้ายตำแหน่ง และแก้ไขรายการในพาเลต |
| ค้นหาการเคลื่อนไหวสินค้า / ประวัติการแก้ไขพาเลต | ตรวจรายการเคลื่อนไหว STOCK CARD และร่องรอยการแก้ไข |
| จุดสั่งซื้อสินค้า / ความพร้อมบรรจุภัณฑ์ (BOM PK) / แผนบรรจุภัณฑ์หลาย FG | ดูจุดสั่งซื้อ ตรวจความพร้อมของส่วนประกอบตามสูตร และวางแผน FG |
| เปรียบเทียบสต็อกพาเลต | เปรียบยอด Stock snapshot กับข้อมูลพาเลต โดยดูเวลาบันทึกของแต่ละแหล่งข้อมูลประกอบ |
| Cycle Counts · ตรวจนับตามรอบ | ตั้งรอบนับตามโซน บันทึกยอดที่ตรวจจริง และส่งออกผลนับเป็น CSV |
| Scrap Inventory · ตัดจำหน่าย | ตัดยอดสินค้าจากพาเลตตามจำนวน/เหตุผล/เอกสารที่ยืนยัน และดูประวัติ Scrap |
| พิมพ์ป้ายตำแหน่งและสินค้า | สร้าง QR ตำแหน่ง `PKLOC` และสินค้า `PKITEM` สำหรับสแกนด้วยกล้องหรือเครื่องอ่าน |
| รายการรับเข้า / รายการเบิก / แผนรับเข้าประจำวัน | ตรวจรายการรายวันและเปิดแผนรับเข้าจากไฟล์ Excel บน Google Drive |

การสแกน QR หรือบาร์โค้ดเพียงอย่างเดียว **ไม่บันทึกการรับ เบิก หรือย้ายสินค้า** ต้องตรวจรายละเอียดและกดยืนยันตามขั้นตอนของแต่ละเมนู กล้องต้องใช้ HTTPS และสิทธิ์กล้องบนอุปกรณ์; ถ้าใช้กล้องไม่ได้ ยังพิมพ์รหัสหรือใช้เครื่องอ่านที่ส่ง Enter ได้

## ข้อมูลและการซิงค์

| แหล่งข้อมูล | ที่เก็บ / พฤติกรรม |
| --- | --- |
| Stock snapshot | เก็บใน Supabase; การอัปเดตใช้ RPC `replace_stock_inventory` และ Update PIN แยกจาก PIN เข้าระบบ |
| พาเลต ตำแหน่ง วันที่รับ และรายการรับเข้า | เก็บใน Supabase; การแก้ไขพาเลตผ่าน `save_pallet_changes` พร้อมตรวจเวอร์ชันเพื่อลดการเขียนทับข้อมูลที่มีคนแก้พร้อมกัน |
| ปฏิทินนัดหมาย | เก็บใน Supabase และซิงค์ข้ามเครื่องผ่าน Realtime/การรีเฟรชระหว่างเปิดหน้าเว็บ |
| แผนรับเข้าประจำวัน | อ่านไฟล์ Excel จาก Google Drive แบบ read-only; รีเฟรชทุก 5 นาทีขณะเปิดแท็บ และรีเฟรชเองได้ การแสดงแผนไม่เพิ่มยอดรับจริง |
| Cycle Counts | ความถี่ ร่าง และผลนับเก็บใน `localStorage` ของเบราว์เซอร์เครื่องนั้น **ไม่ซิงค์ข้ามเครื่อง**; ส่งออก CSV เพื่อเก็บหลักฐาน |
| แผน BOM หลาย FG | ร่างแผนเก็บในเบราว์เซอร์; ตรวจผลกับข้อมูลสต็อกที่โหลดในหน้าเว็บ |

**Stock snapshot กับยอดพาเลตเป็นข้อมูลคนละชุด** การตัดจำหน่าย Scrap ลดจำนวนในพาเลต แต่ไม่ปรับ Stock snapshot, บัญชี หรือคำสั่งซื้อทดแทนอัตโนมัติ ผล Cycle Counts ก็ไม่ปรับยอดพาเลตหรือ Stock โดยอัตโนมัติ

ปฏิทินนัดหมายและรายการแจ้งเตือนในกระดิ่งทำงานเมื่อเปิดเว็บอยู่ Popup แจ้งเตือนจะจางหาย ส่วนรายการในกระดิ่งยังคงอยู่ตามสถานะของระบบ ฟังก์ชันนี้ไม่ใช่ Push Notification เมื่อปิดเว็บ

## การเข้าสู่ระบบและสิทธิ์

เว็บใช้ Supabase Auth และ Edge Function [`pk-user-access`](supabase/functions/pk-user-access/index.ts) สำหรับเข้าสู่ระบบด้วยชื่อผู้ใช้ จัดการผู้ใช้ และกำหนดสิทธิ์รายเมนู มี Admin ได้หนึ่งบัญชี ผู้ใช้ย่อยไม่ต้องระบุอีเมลใน UI; ระบบสร้างอีเมลภายในให้ Supabase Auth เอง PIN ผู้ใช้ย่อยถูกแปลงเป็นรหัสผ่านฝั่ง Edge Function ไม่เก็บ PIN ในไฟล์เว็บหรือ GitHub

สิทธิ์เมนูอยู่ใน `app_users.menu_access`; หน้าเว็บซ่อนเมนูที่ไม่ได้รับสิทธิ์ และ [กฎฐานข้อมูล](supabase-menu-access.sql) จำกัดการอ่าน/เขียนข้อมูล Supabase หลักตามสิทธิ์ที่เกี่ยวข้อง การปิดบัญชีทำให้ใช้ฐานข้อมูลด้วย JWT เดิมไม่ได้อีก ก่อนใช้งานจริงต้องมีทั้งหน้าเว็บ, SQL migration และ Edge Function เวอร์ชันที่สอดคล้องกัน

**ขอบเขตความปลอดภัย:** ข้อมูลบางชุดยังฝังใน `index.html` หรือไฟล์ JavaScript ที่โฮสต์แบบสาธารณะ การซ่อนเมนูไม่ทำให้ข้อมูลเหล่านั้นเป็นข้อมูลลับ หากต้องแยกข้อมูลตามผู้ใช้จริง ต้องย้ายข้อมูลไป API ที่ตรวจสิทธิ์ก่อนส่งกลับ คีย์ publishable ของ Supabase อยู่ในเว็บได้ แต่ **ห้ามนำ service-role key, Update PIN หรือรหัสผ่านขึ้น GitHub**

## โครงสร้างโปรเจกต์และการพัฒนา

| ไฟล์ / โฟลเดอร์ | หน้าที่ |
| --- | --- |
| [`index.html`](index.html) | หน้าเว็บหลักและข้อมูล/ตรรกะ Dashboard บางส่วน |
| `*.js`, `*.css` ที่ root | ฟังก์ชันเมนู, การซิงค์, ธีม และการแสดงผลแต่ละงาน |
| [`supabase/`](supabase/functions/pk-user-access/index.ts) และ `supabase-*.sql` | Edge Function และประวัติ migration ของฐานข้อมูล |
| [`tests/`](tests/) | การทดสอบหน่วย การถดถอย และเอกสาร QA |
| [`docs/ODOO-19-ADOPTION.md`](docs/ODOO-19-ADOPTION.md) | แนวทางเตรียมข้อมูลพาเลตสำหรับ Odoo 19 Community; เว็บนี้ไม่ได้เชื่อม Odoo โดยตรง |
| [`DESIGN.md`](DESIGN.md), `wms-operations.css` | แนวทางออกแบบและธีม UI ปัจจุบัน |

หน้าเว็บเป็น static site ที่ root ของ repository ไม่มีขั้นตอน build หรือ `package.json` สำหรับเว็บหลัก เปิดทดสอบในเครื่องผ่าน HTTP แทนการเปิด `file://`:

```powershell
python -m http.server 8000
# เปิด http://localhost:8000/
```

ต้องต่ออินเทอร์เน็ตสำหรับ Supabase, Google Drive, Google Fonts และไลบรารีจาก CDN บางส่วน การเข้าใช้ข้อมูลจริงยังต้องมีบัญชีที่ได้รับสิทธิ์

ทดสอบส่วนที่แก้ไขด้วย Node.js จาก root ของ repository เช่น:

```powershell
node tests/user-access-no-email.test.mjs
node tests/pallet-security.test.cjs
node tests/cycle-counts.test.cjs
node tests/scrap-inventory.test.cjs
```

การทดสอบฐานข้อมูลแบบแยกสภาพแวดล้อมมีคำอธิบายใน [`tests/DATABASE-TESTING.md`](tests/DATABASE-TESTING.md) บันทึก QA รุ่นเก่าใน `tests/` อาจอธิบายข้อจำกัดของรุ่นก่อนหน้า ให้ยึดโค้ดและ schema ปัจจุบันเมื่อเปลี่ยนระบบ

## การเผยแพร่และการเปลี่ยนฐานข้อมูล

เว็บเผยแพร่เป็นไฟล์ static จาก branch `main` ของ repository นี้บน Vercel และ GitHub Pages การแก้โค้ดเว็บให้ commit/push แล้วตรวจหน้าเว็บที่เผยแพร่จริง รวมทั้งไฟล์ CSS/JS เวอร์ชันใหม่เมื่อมีการเปลี่ยน cache key

ไฟล์ SQL ใน repository เป็น **บันทึก migration ของโปรเจกต์ Supabase ที่ใช้อยู่** ไม่ใช่ชุดคำสั่งที่ต้องรันซ้ำทุกครั้งหรือชุดติดตั้งฐานใหม่แบบคลิกครั้งเดียว โดยเฉพาะ [`supabase-user-login.sql`](supabase-user-login.sql) และ [`supabase-menu-access.sql`](supabase-menu-access.sql) ต้องพิจารณาลำดับและสถานะ schema ก่อนรัน ส่วนการแก้ [`pk-user-access`](supabase/functions/pk-user-access/index.ts) ต้อง deploy Edge Function แยกจากการ push หน้าเว็บ และคง service-role key ไว้ใน Supabase เท่านั้น

การเตรียมข้อมูลพาเลตเพื่อใช้กับ Odoo 19 Community และตัวแปลงส่งออกอยู่ใน [`docs/ODOO-19-ADOPTION.md`](docs/ODOO-19-ADOPTION.md) และ [`tools/odoo-pallet-export.mjs`](tools/odoo-pallet-export.mjs)
